# Spec for Signup Firebase Auth Integration

branch: claude/feature/signup-firebase-auth
figma_component (if used): none

## Summary
Wire the existing `SignupForm` (`components/SignupForm/`) to real Firebase Authentication, using the `auth` and `db` exports already initialized in `lib/firebase/config.ts`. On successful account creation, the new user is given a randomly generated "codename" — a display name assembled by picking one word from each of three distinct, non-overlapping word lists and joining the words together in PascalCase (e.g. `SilentShadowFox`) — which is set as the Firebase Auth user's `displayName`. A corresponding document is also created in a Firestore `users` collection recording the codename and the user's id, but never their email. Only the Firebase Web SDK (client-side, modular `firebase/*` imports) is used — no Admin SDK, no server actions, no API routes. The `LoginForm` and its submit behavior are out of scope and remain the current stub.

## Functional Requirements
- `SignupForm`'s submit handler creates a new Firebase Auth account from the entered email and password using the Web SDK's email/password sign-up call, sourced from the shared `auth` export in `lib/firebase/config.ts`.
- On successful account creation, a codename is generated by selecting one word at random from each of three separate word lists, then concatenating the three chosen words with no separator, each word capitalized (PascalCase), e.g. `Word1Word2Word3`. The three lists are distinct from one another (a word does not appear in more than one list), and each list's own words are unique (no duplicates within a list).
- The generated codename is set as the newly created user's `displayName` via the Web SDK's profile-update call.
- A document is created in a Firestore `users` collection (via the shared `db` export) recording the user's `codename` and their `id`. The user's email is never written to this document or to any other Firestore document as part of this feature.
- Only Firebase Web SDK modular imports (`firebase/auth`, `firebase/firestore`) are used for every step of this flow — account creation, profile update, and the Firestore write.
- If account creation fails (e.g. email already registered, malformed email, weak password) or the follow-up profile/Firestore steps fail, the failure is surfaced to the user on the signup page rather than failing silently or only logging to the console.
- The submit control is disabled (or otherwise prevented from re-submitting) while a signup attempt is in flight, so a user cannot trigger a second concurrent signup from the same form.
- `LoginForm` is not modified as part of this feature and keeps its current placeholder submit behavior.

## Possible Edge Cases
- The email is already registered to an existing account.
- The password does not meet Firebase's minimum requirements.
- The email field is malformed (client-side `noValidate` means the browser won't block this before submit).
- The network request fails or times out partway through the flow (e.g. the Auth account is created but the subsequent profile update or Firestore write fails) — the user-facing error state should not claim total failure if the account was in fact created.
- The user double-clicks submit or presses Enter twice in quick succession before the first request resolves.
- Two different signups happen to generate the same codename (low-probability word-combination collision) — no uniqueness enforcement against existing codenames is assumed unless called out as a requirement.
- The user navigates away from the signup page before the async signup flow resolves.

## Acceptance Criteria
- Submitting the signup form with a valid, unused email and a valid password creates a new Firebase Auth user.
- The created user's `displayName` is a three-word PascalCase codename, with each of the three words drawn from a distinct word list.
- A document exists in the Firestore `users` collection for the new user containing its `codename` and `id`, and does not contain the user's email address.
- Submitting with an email that's already registered surfaces a visible error on the signup page and does not create a duplicate account.
- The submit control cannot fire a second signup request while one is already in flight.
- No Firebase Admin SDK, server action, or API route is used anywhere in this flow — every call goes through the client-side Web SDK.

## Open Questions
- Should the Firestore document's ID be the user's Firebase Auth `uid` itself, or an auto-generated document ID with a separate `id` field storing the `uid`? **Yes use firebase documents ID**
- On successful signup, should the user be redirected anywhere (e.g. to `/heists`), or does this feature end at account + Firestore doc creation with no navigation change? **Redirect to heists**
- What are the three word lists' theme and contents (e.g. heist/spy-themed adjectives and nouns to match the app's premise)? Any exact words, or an open set to be chosen during implementation? **Open set to be chosen during implementations**
- How should signup errors be displayed on the page (e.g. inline message under the form, using existing error styling tokens) — is any new shared UI needed, or does an existing pattern already cover this? **Lets go with inline message under form, add any UI needed to accommodate this**

## Testing Guidelines
Create a test file(s) in the ./tests folder for the new feature, and create meaningful tests for the following cases, without going too heavy:
- Submitting valid signup details calls Firebase Auth account creation with the entered email and password.
- On success, the generated codename follows the PascalCase, three-distinct-list-word format.
- On success, a Firestore document is written to the `users` collection containing `codename` and `id`, and never an `email` field.
- On an account-creation failure (e.g. email already in use), an error is surfaced on the page and no Firestore document is written.
- The submit control is disabled/prevented from re-firing while a signup request is in flight.
